# API Alignment: Frontend ↔ Contract v1

How the frontend maps onto [API_CONTRACT.md](API_CONTRACT.md) (regenerated from the backend
on 2026-11-12), where the contract and the
designs disagree, and what we need the backend to answer. Item IDs (M1, Q3…) are referenced from
code comments in `frontend/src/types/api/`, so keep the numbering stable. Mark items resolved; don't delete them.

**Status legend:** 🔴 blocks a planned phase · 🟡 workaround in place, should fix · ⚪ clarification

## 1. What the frontend now does

| Contract rule                     | Frontend implementation                                                                                                                              |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Base URL `/api/v1`                | `VITE_API_BASE_URL` defaults to `/api/v1`. Vite proxies `/api` and `/static` to FastAPI in dev                                                       |
| Error envelope `{ error: {…} }`   | `ApiError` exposes `status`, `code`, `message`, `details[]`, `timestamp`, `fieldErrors`. It also parses FastAPI's default `{ detail }` as a fallback |
| Bearer JWT                        | `Authorization: Bearer <access_token>` attached automatically from `tokenStorage`                                                                    |
| 401                               | One refresh + replay; if that fails, tokens are cleared and the `AuthProvider` handler sends the user to `/login`                                                                  |
| JSON + multipart upload           | `api.get/post/put/patch/delete` + `api.upload(path, { file })`                                                                                       |
| Query params                      | `query` option. `undefined` values skipped, arrays repeated                                                                                          |
| Inches, top-left origin           | UI keeps the user's unit and converts at the boundary (`lib/units.ts`)                                                                               |
| Money as decimal strings          | Typed as `DecimalString`, displayed only via `formatMoney()`. No client-side arithmetic                                                              |
| Relative asset URLs (`/static/…`) | `resolveApiUrl()` resolves them against the API origin                                                                                               |
| Every endpoint                    | Paths in `services/endpoints.ts`. Request/response types in `types/api/*` (snake_case, 1:1 with the wire)                                            |

Auth calls are wired (`services/authService.ts`, Phase 4). The planner, designs, photos and quotes are not (Phase 5).

### Resolved by Backend Phase 2 (2026-11-12)

- **Q2:** `POST /auth/refresh` and `POST /auth/logout` exist. Rotation is atomic and safe for
  concurrent tabs; logout revokes the session server-side.
- **Q3:** the refresh token is **only** an httpOnly, SameSite cookie scoped to `/api/v1/auth`. It no
  longer appears in any response body (`AuthTokens` = `access_token`, `token_type`, `expires_in`).
  The frontend keeps the access token in memory (`services/tokenStorage.ts`) and restores a session
  after reload by calling `/auth/refresh`. `apiClient` sends `credentials: 'include'` and
  `X-CSRF-Protection: 1` on every non-GET request, which the cookie endpoints require.
- **Q17:** login is limited per IP + account (5/5 min), per account (20/15 min) and per IP
  (30/5 min); `429` carries `Retry-After`. Unknown accounts and wrong passwords return the same `401`
  with the same Argon2id cost.
- **Q18:** identifier ≤ 254, phone ≤ 20, password ≤ 128 enforced server-side; bodies over 1 MiB are
  rejected with `413 PAYLOAD_TOO_LARGE`. Error text never includes stack traces, driver messages or
  echoed input.
- **Q11 (partly):** every error, including CSRF (`CSRF_VALIDATION_FAILED`), oversize
  (`PAYLOAD_TOO_LARGE`) and unhandled 500s, uses the `{ error: {…} }` envelope.

### Resolved by Backend Phase 3 (2026-11-12)

The contract was regenerated from the implementation ([API_CONTRACT.md](API_CONTRACT.md) §11
lists the changes); `src/types/api/*` and `services/endpoints.ts` follow it, and
`backend/tests/test_catalog_contract.py` checks the endpoint map and the planner catalog against
the frontend sources.

- **Q1:** IDs are ObjectId strings; `EntityId = string`.
- **M3:** `POST /auth/google` and the three forgot-password endpoints exist (contract §2);
  wiring the existing UI to them is frontend Phase 4.
- **M8, M9:** `GET /catalog` publishes frame sizes, wood finishes (hex + `profile_inches`),
  mount colours, paint shades, layout styles and the planner rules, all with stable IDs. Moulding
  colours carry the same finish IDs. Version items store `size_id`, `finish_id` and
  `matting.color_id`; walls store `paint_id`. Orientation is stored per item.
- **M6:** template categories and `layout_type` are `grid`, `salon`, `centre`, `row` (+ `custom`).
  `focal_center`, `triptych` and `linear` are normalised. `LAYOUT_STYLES.apiCategory` is 1:1.
- **M4:** geometry uses `outer_*_inches` and one `BoundingBox { x, y, width, height }`. Pricing
  names are gone with the pricing endpoint.
- **M5:** login returns the full `User`.
- **M7:** `GET /designs` (paginated), `PATCH` and `DELETE` exist.
- **M10 (partly):** generate/regenerate/redesign accept placeholder frames (no `photo_id`) and
  catalog `size_id`/`finish_id`, with `seed`/`variant`. A multi-variant `layouts[]` response
  doesn't exist; the planner keeps its client-side carousel.
- **M12:** versions take typed `layout_metadata` (style, gap, gap unit, seed, variant) and
  `preview` (sofa, index badges, guides). Eye level is a fixed rule (60 in).
- **Q5:** photo thumbnail/preview URLs are signed and short-lived, so `<img src>` works.
- **Q6, Q9 (partly):** enums are in the contract (layout styles, statuses, units). `glass_type`
  stays free text (`standard`) until glazing options exist.
- **Q7, Q8:** there is no online pricing; quotes go to WhatsApp and the studio prices them.
- **Q10:** `validate-layout` always answers 200 with collisions in `errors[]` (with `item_ids`).
  Saving a version that doesn't fit is a 422 with `details[].field = items.<item_id>`.
- **Q11, Q13:** one envelope for everything; codes are listed in contract §1.4. `details[].field`
  is the request path (`email`, `wall.width_inches`, `items.0.finish_id`).
- **Q12:** `?page&page_size` for designs and photos.
- **Q14:** photos ≤ 25 MB, 300–8192 px per side; quote previews ≤ 15 MB.
- **Q15:** India only (`+91`), validated server-side.
- **Q19:** 8–128 characters with a letter and a digit (same as the UI); duplicates → 409
  `ACCOUNT_ALREADY_EXISTS` with `details[].field` = `email`/`phone`; Unicode names (e.g.
  Devanagari) are accepted.
- **Q20 (partly):** the server validates with `EmailStr`; whether to widen the client check for
  internationalised addresses is still open.
- **Q21, Q22:** the server is the source of truth for fit and catalog references, using the same
  rules as the planner (wall 36–480 × 48–240, gap 0–12, mount 0–6, 1–16 frames, 6 in margin,
  12 in above the floor or above the sofa). Photo references must be the user's own photo IDs.
  The planner should block **Save** while the layout doesn't fit, or the save will fail.
- **Still open:** Q4 (production origin), Q16 (planner before sign-in), M11 (export stays
  client-side unless a server export is wanted).
